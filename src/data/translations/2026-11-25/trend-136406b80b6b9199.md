### 무엇인가요

Agent Anomaly Detection(AAD)은 에이전트의 행동이 의도한 범위를 벗어났을 때 그것을 파악하고 대응하도록 돕는 기능이에요. 지정한 로깅·관측 버킷의 추적과 로그를 분석하기 때문에 에이전트 런타임에 접근할 필요가 없어요. 처음에는 구글 클라우드의 Agent Runtime, Cloud Run, GKE에서 돌아가는 에이전트를 다뤘고, 이번 글은 다른 클라우드와 온프레미스 에이전트까지 범위를 넓힌 내용이에요.

### 텔레메트리 요건

어느 환경에서 보낸 텔레메트리든 Telemetry API(`telemetry.googleapis.com`)로 들어오면 분석할 수 있어요. 이 경로는 에이전트를 식별하는 리소스 속성을 그대로 유지해요. 텔레메트리는 OpenTelemetry 규약을 따라야 하고, 프롬프트와 응답은 로그 이벤트로 기록해야 해요. AAD는 그 로그 이벤트에서 대화를 읽어요. 글의 ADK 설정은 다음 변수를 써요.

- `OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental` — 새 GenAI 시맨틱 규약을 선택해요.
- `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=EVENT_ONLY` — 메시지 내용을 이벤트로 수집해요.
- `ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false` — 메시지 내용을 스팬에는 넣지 않아요.
- `OTEL_SERVICE_NAME` — 에이전트 이름을 지정해요.
- `OTEL_RESOURCE_ATTRIBUTES` — `cloud.provider`, `cloud.region`, `faas.name`처럼 공급자·플랫폼·리전·함수명을 적어요.

### 지원 환경

구글 클라우드는 Agent Runtime, Cloud Run, GKE를 지원해요. AWS 예시는 AWS Lambda에서 돌아가는 재고 관리 에이전트이고 Amazon Bedrock 모델도 쓸 수 있어요. Azure 예시는 Microsoft Foundry에 호스팅된 고객 서비스 에이전트예요. 온프레미스 에이전트도 사용 사례로 언급되는데, 위 조건을 충족하는 텔레메트리를 보내는 환경이면 모두 해당돼요.

### 탐지 유형

- **연쇄 실패**: 서로 맞물려 증폭되는 루프와 반복 호출이에요.
- **자원 소진**: 토큰, 연산, 도구 호출의 폭주예요.
- **신원·권한 남용**: 사용자가 관리자 권한을 주장하는 식으로 에이전트가 역할을 넘어 행동하는 경우예요.
- **도구 오용**: 삽입된 텍스트로 환불이 실행되는 것처럼 도구가 의도와 다르게 쓰이는 경우예요.

각 발견 항목에는 도구 호출 속도 제한, 도구 인자 검증, 임계값 초과 시 추가 확인 같은 권고가 함께 붙어요.

### 설정 절차

1. Agent Anomaly Detection 개요 페이지에서 프라이빗 프리뷰 접근을 신청해요.
2. Workload Identity Federation을 구성해 에이전트가 자신의 신원(AWS 역할이나 Microsoft Entra 아이덴티티)을 단기 구글 자격 증명으로 교환하게 해요. 서비스 계정 키는 필요 없어요.
3. ADK for Python 2.12.0 이상으로 계측하고, ADK의 구글 클라우드 익스포터와 위 환경 변수를 써요.
4. 약 30분 안에 에이전트가 Monitored agents 목록에 나타나요.
5. 모니터링을 수동으로 켜거나, 탐지 시점에 자동 등록되도록 설정해요.

에이전트의 모델 호출과 도구 호출은 원래 실행 위치에서 그대로 돌아가고 텔레메트리만 구글 클라우드 프로젝트로 가요. 분석은 따로 돌아가므로 에이전트를 느리게 만들지 않아요.

### 제공 상태

AAD는 구글 클라우드 외부 에이전트 모니터링까지 포함해 프라이빗 프리뷰예요. 현재 외부 경로는 ADK for Python 에이전트를 지원하고, 외부 에이전트의 발견 항목은 AAD 콘솔에서만 볼 수 있어요. 구글 클라우드에서 돌아가는 에이전트는 같은 탐지기와 콘솔을 함께 쓸 수 있어요.
