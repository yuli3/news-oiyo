### 세 가지 문제

- **내부 전용 인그레스**: 내부 인그레스를 켜면 Gemini Enterprise의 기본 공개 호출이 구글 엣지에서 HTTP 404로 실패해요.
- **두 개의 신원 확인**: Cloud Run IAM은 요청이 인가된 Gemini Enterprise 인스턴스에서 왔는지 확인해야 하고, MCP 앱은 사용자의 OAuth 2.0 토큰을 검증해야 해요.
- **공유 VPC의 DNS 충돌**: `*.run.app` 와일드카드 사설 영역을 만들면 네트워크 안의 모든 Cloud Run 서비스의 DNS를 덮어써요.

### 구조

Gemini Enterprise는 구글이 관리하는 테넌트 프로젝트에서 돌아가므로, 서버리스 Cloud Run 서비스에 닿으려면 네트워크 홉 두 개와 범위를 좁힌 DNS 조회 하나가 필요해요.

**브리지 1**은 Agent-to-Anywhere 모드의 리전 Egress Agent Gateway예요. 리전 서브넷의 PSC 네트워크 어태치먼트에 연결해, 공개 IP도 인바운드 방화벽 규칙도 없는 관리형 인터페이스를 VPC 안에 만들어요(글은 us-central1 또는 europe-west1을 예로 들어요).

**브리지 2**는 VPC에서 Cloud Run으로 가는 사설 경로이고 두 가지 선택지가 있어요.

| | 옵션 A: 서브넷 Private Google Access | 옵션 B: 글로벌 PSC 엔드포인트 |
|---|---|---|
| 대상 VIP | 199.36.153.8/30 | 240.0.0.10 |
| 추가 리소스 | 없음 | 글로벌 내부 IP와 all-apis 전달 규칙 |
| 적합한 환경 | 기본 0.0.0.0/0 경로를 유지하는 VPC | 기본 인터넷 경로를 제거한 폐쇄형 VPC |

**DNS는 호스트명 단위로** 좁혀요. 사설 DNS가 없으면 `.run.app` 이름이 인터넷 IP로 풀려서 PSC 어태치먼트에 외부 경로가 없는 탓에 HTTP 502로 타임아웃이 나요. 와일드카드 대신 MCP 서비스의 정확한 호스트명만 담은 Private Cloud DNS 영역을 만들고 그 이름만 게이트웨이와 피어링해요. Cloud DNS는 가장 긴 접미사 일치를 쓰기 때문에 공유 VPC의 다른 서비스는 그대로 해석돼요. 게이트웨이는 사설 VIP로 접속하면서도 TLS SNI와 HTTP Host 헤더에 서비스 호스트명을 유지해 Cloud Run이 올바른 컨테이너로 라우팅하게 해요.

**이중 헤더 신원 확인**은 이렇게 나뉘어요. `X-Serverless-Authorization`은 Gemini Enterprise 서비스 에이전트의 구글 서명 OIDC ID 토큰을 담고, Cloud Run IAM이 Invoker 역할과 대조한 뒤 컨테이너에 닿기 전에 제거해요. `Authorization: Bearer`는 로그인한 사용자의 OAuth 2.0 액세스 토큰을 그대로 전달해 미들웨어가 사용자별 권한을 적용해요. 예제 `OAuth2ValidationMiddleware`는 `/health`는 건너뛰고, `REQUIRE_OAUTH`가 설정되면 토큰이 없거나 잘못된 요청을 401로 막아요.

### 설정 절차

1. StreamableHTTP MCP 서버를 내부 인그레스와 IAM 인증으로 배포하고, Gemini Enterprise 서비스 에이전트에 Invoker 역할을 줘요.
2. 서브넷에 Private Google Access를 켜고 자동 수락 PSC 네트워크 어태치먼트를 만든 뒤, Egress Agent Gateway를 만들어 서비스 계정 권한을 주고 어태치먼트를 붙이고 아웃바운드 인가 정책을 적용해요.
3. 정확한 호스트명만 담은 사설 영역을 만들고 A 레코드를 구글 VIP(폐쇄형 VPC는 내부 PSC IP)로 지정한 뒤, 그 호스트명 하나에 DNS 피어링을 설정해요.
4. Gemini Enterprise의 Security Configuration에서 게이트웨이를 앱에 바인딩하고, 커스텀 MCP 서버 데이터 스토어를 엔드포인트와 OAuth 2.0 클라이언트 자격 증명으로 등록한 뒤 게이트웨이 이그레스와 Actions 모드를 켜요.
5. 커스텀 액션을 리로드하고 테스트 프롬프트를 돌려, 탐색과 도구 호출이 게이트웨이를 지나고 IAM·OAuth 검사를 모두 통과하는지 Cloud Logging에서 확인해요.

### 주의할 점

옵션 A는 기본 인터넷 경로에 의존하므로 폐쇄형 VPC는 옵션 B가 필요해요. 사설 영역은 호스트명 하나만 덮으니 새 서비스 URL마다 영역과 피어링을 따로 만들어야 하고, 공유 VPC는 추가 IAM 바인딩이 필요해요. 예제 코드는 `_verify_google_oauth_token`이 빠져 있고 `has_serverless_auth` 변수는 할당만 되고 쓰이지 않아 미들웨어가 인프라 헤더를 직접 검사하지는 않아요. 글은 운영 환경 검증 결과를 제시하지 않고, 절차가 여러 구글 클라우드 제품에 의존한다는 점도 함께 알아둘 필요가 있어요. GitHub 저장소에 예제 서버와 Dockerfile, 스모크 테스트, 설정 스크립트, 공유 VPC IAM 바인딩이 들어 있어요.
