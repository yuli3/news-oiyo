Michał Górny가 2026년 10월 27일 블로그에 쓴 글이에요. 2021년에 쓴 "The modern packager's security nightmare" 이후 상황이 나아졌는지 묻는 데서 시작해요.

### 핵심 주장
- 저자는 상황이 나아지지 않았고, 끝이 보이지 않는 내리막길에 들어선 느낌이라고 말해요.
- 취약점 보고가 전례 없는 속도로 늘고 있어요. 의존성 트리의 한 가지가 믿을 수 없게 되면 그 아래 사람들이 더 큰 부담을 떠안아요.
- 소프트웨어가 예전보다 덜 안전해졌는지는 확답하지 않아요. 기업, 마케팅 중심 개발, Rust의 메모리 안전성 강조, AI 생성물(slop)을 탓하고 싶지만 원인은 확실하지 않다고 적어요.

### 보고 홍수와 판단의 어려움
- 이제 누구나 chatbot을 써서 보안 연구자가 될 수 있어요. slop 때문에 버그 바운티는 거의 사라졌지만 보고는 계속 들어와요.
- 명백히 잘못된 보고를 걸러내도 남는 보고가 많아요. 중요도를 판단하고, 제출된 수정이 유효하며 회귀를 일으키지 않는지 확인해야 해요.
- REDoS 같은 성능 버그가 취약점인지는 공격 경로에 따라 달라요. 억지스러운 시나리오도 있지만, 타이밍 공격으로 사용자의 비밀을 추측할 수 있는 경우처럼 심각한 문제도 있어요.

### 메인테이너가 처한 현실
- 판단할 능력이 있어도 이미 CVE가 붙어 있고 점수가 지나치게 높으면, 보안 스캐너가 계속 경고하고 사용자가 항의하거나 포크하는 일이 생겨요.
- 저자는 Gentoo에 영향이 없는데도 스캐너 오탐을 피하려고 불필요한 보안 stabilization을 했고, "outdated" 표시를 피하려고 실질적 변경이 없는 버전 범프도 했다고 털어놓아요.

### 보안 대응 체계의 부족
- 대부분의 프로젝트는 보안 이슈를 처리할 준비가 되어 있지 않다고 지적해요. LTS나 보안 브랜치가 없고, 최소 변경으로 보안 릴리스를 내는 일도 드물어요.
- 보안 수정에 새 기능, deprecation, API 변경이 섞이는 경우가 흔해서, downstream은 취약한 버전을 벗어나려고 큰 API 변화에 대응해야 해요.

### 결론
- 결국 커뮤니티가 한계에 이르고, 서로에게 기대지 못해 각자 더 많은 것을 번들링하게 된다고 해요. 저자는 이 흐름을 "every chatbot for itself"라는 말로 요약해요.
- 댓글에서는 CRA가 이 문제를 다루려 했지만 번들링의 여지를 남겼다는 지적과, 제로데이가 사라지지는 않을 것이라는 반박이 나왔어요.
