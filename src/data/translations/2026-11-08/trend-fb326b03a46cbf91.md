vc-bench 사이트의 결과 매트릭스와 시나리오 설명 앞부분을 읽고 정리했어요.

### 무엇을 재나

각 시나리오는 미리 만든 Git 저장소와 평이한 영어 지시문으로 이뤄져요. 실행 중 코드는 쓰지 않고 **버전 관리 작업만** 측정해요. 도구는 git, Jujutsu, GitButler 세 가지이고, Codex와 Claude 두 에이전트가 같은 매트릭스를 돌려요. 사이트는 이것이 Claude 대 Codex 비교가 아니라, 도구 효과가 모델이 바뀌어도 유지되는지 확인하려는 것이라고 밝혀요.

### 결과(페이지 기본 표시 기준)

- 6개 시나리오(선택 커밋, 여러 커밋 amend, 커밋 분할, 커밋 순서 변경, squash, 더러운 브랜치 업데이트) 모두 세 도구가 10/10을 통과했어요. 전체로는 각각 60/60(95% CI 94~100%)이에요.
- 평균 시간·명령 수·KB: git 92.2초·20.4개·31.7KB, Jujutsu 110초·21.0개·46.1KB, GitButler 34.0초·4.5개·13.3KB
- git 대비 시나리오별 짝지은 차이: **GitButler**는 시간 −58.2초[−106, −10.7], 명령 −15.8개[−26.0, −5.7]로 효과가 확인됐어요. **Jujutsu**는 시간 +17.6초[−23.3, +58.6], 명령 +0.6개로 구간이 0을 지나 효과가 확립되지 않았어요.
- KB는 한 에이전트 안에서만 비교 가능하다고 적혀 있어요.

### 시나리오 예시

1. **섞인 작업 트리에서 선택 커밋**: 입력 검증 수정과 무관한 로깅·설정·디버그 메모 편집이 섞여 있어요. 검증 작업만 새 브랜치의 커밋 하나로 만들어야 해요. 핵심은 `src/handler.ts` 한 파일에 검증 hunk 두 개와 남겨야 할 로깅 hunk가 같이 있다는 점이에요.
2. **여러 이전 커밋에 수정 amend**: 5개 커밋 브랜치의 미커밋 변경을 해당하는 세 커밋에 새 커밋 없이 amend로 나눠 넣어야 해요. 같은 파일(`src/lead.ts`, 테스트, README)이 여러 대상 커밋에 걸쳐 있어 한 파일을 쪼개야 해요.
3. **중간 커밋 분할**: 검증·점수·문서 변경과 디버그 편집이 섞인 중간 커밋을 순서 있는 단일 목적 커밋 셋으로 나누고 디버그 편집은 작업 트리로 돌려야 해요.
