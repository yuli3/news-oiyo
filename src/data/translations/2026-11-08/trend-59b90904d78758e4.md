### 동기

작성자는 HP 계산기로 RPN(역폴란드 표기)을 배웠고 Forth에 꽤 많은 시간을 썼어요. Qwenputer가 기계를 언어 모델 가중치에 컴파일하는 걸 보고 두 가지가 궁금했어요. 스택 언어가 그 아이디어에 잘 맞을까? 활성 파라미터 3B짜리 모델이 그런 기계를 다룰 수 있을까?

### 구성

- NVIDIA Nemotron 3.5 Lightning(30B, 활성 3B)은 그대로 둬요.
- 같은 모델 안에 27개 레이어로 된 두 번째 네트워크를 붙였어요. 가중치는 Python 스크립트가 계산했고 학습한 건 하나도 없어요. 이게 Forth 인터프리터예요.
- 모델이 Forth 블록을 평범한 텍스트로 쓰면, 인터프리터가 모델이 쓰는 동안 순전파 한 번에 한 단계씩 각 단어를 실행해요. 블록이 닫히면 결과를 모델의 다음 토큰으로 써요. 도구 호출도 없고 생성도 멈추지 않아요.

### 왜 RPN이 잘 맞나

Forth 단어는 공백에서 끝나서, 전체 프로그램을 파싱하지 않고 다음 단어가 시작되는 즉시 실행할 수 있어요. 피연산자가 연산자보다 먼저 오니, 모델이 +를 쓸 때 두 수가 이미 스택에 있어요. 왼쪽에서 오른쪽으로 쓰는 모델의 순서와 맞아요.

### 정확하게 만들기

- 스택은 Mamba-2 상태에 살아요. 항목 하나가 20자리 폭의 한 행이고, 꺼낼 때는 정확한 음수를 더해요.
- bf16은 256까지만 정수를 정확히 담아서, 기계 안의 어떤 값도 그 이상 올라가지 않게 했어요.
- Mamba 감쇠를 모두 정확히 1로 둬서 아무것도 흐려지지 않아요.
- 내부 단계에는 모델이 쓰지 않고 빈 문자열로 디코딩되는 예약 토큰 982개를 써요. 테스트에서 기계 토큰 765,734개가 모두 Python 기준 구현과 일치했어요.

### 어려웠던 건 모델 쪽

작은 Qwen 모델로 만든 이전 버전은 기계는 정확했지만 모델이 그걸 쓰지 못했어요. 기본 Lightning은 더 나았지만 결과를 믿지 않았어요. 한 기록에선 기계에서 맞는 답을 받고도 손으로 긴 나눗셈을 하다 토큰을 다 썼고, 쉬운 문제에서 기계가 있을 때 점수가 더 낮기도 했어요. LoRA 파인튜닝으로 대부분 고쳐, 600문제 홀드아웃 테스트 점수가 79.1%에서 92.1%로 올랐어요.

Qwenputer 산술 세트에선 결과가 엇갈려요. DeepMind 세트에선 기본 Lightning과 비슷했는데, 30B 사고형 모델이 그 문제들엔 기계가 거의 필요 없기 때문이에요. 긴 정수에선 기계가 20자리에서 멈춰 Python에 졌어요. 작성자는 이것이 연구용 실험이라고 밝혀요.
