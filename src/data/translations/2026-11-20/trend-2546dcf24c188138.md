OpenAI 엔지니어링 글(2026년 11월 19일, Okay Zed·Cyrus Forbes)의 약 1만 4천 자, 수정 단계 설명까지 읽고 옮겼어요. 그 뒤의 평가 루프와 교훈 정리 일부는 옮기지 않았어요.

### 왜 만들었나

에이전트 개발 속도가 엄청나게 빨라지면서 전통적인 성능 엔지니어링으로는 따라갈 수 없게 됐다고 해요. 그래서 Codex와 모델의 능력을 모두 써서 회귀를 찾고 고치는 자율 시스템 Performance Factory를 클라우드에 만들었어요. 엔지니어는 반복 작업용 워크플로를 정의하고 Codex 에이전트가 따를 지침을 써요. Regression Workflow는 성능 경보가 울리면 작업을 열고, 에이전트가 조사해 결과를 기록하고 수정안을 제안하며, 배포 후 다른 에이전트가 기준선으로 돌아왔는지 확인해요. 3개월 남짓 동안 1,700건 이상을 조사하고 600건 이상의 근본 원인을 찾았어요. 하루 17건꼴이에요.

### 수동 조사에서 공장까지 6단계

1. **Codex 이전**: 지표·로그·트레이스를 손으로 보고 라이브 머신을 디버깅했어요. 첫 토큰 지연 같은 반복 문제용으로 CPU·할당 프로파일러 등 성능 도구가 30개 넘게 쌓였어요.
2. **파트너 Codex**: "왜 느려졌지?"라고 물으면 Codex가 코드베이스를 뒤지고 서비스 간 상호작용을 따라가 프로파일링했지만, 방향은 엔지니어가 잡았어요.
3. **재사용 스킬**: 조사 절차를 perf-forensics 스킬로 담았어요(느려진 시점, 영향받은 요청, 배포·설정 변경 여부). 과거 회귀로 만든 eval로 다듬어, 경보 하나로 한 번에 진단을 받게 됐어요.
4. **사람 프록시**: 엔지니어가 경보를 Codex에 붙여 넣고 결과를 Slack에 다시 붙이는 중계자가 됐어요.
5. **자동 조사**: 경보가 클라우드에서 Codex 세션을 자동으로 시작했지만, 수정과 검증은 여전히 사람이 했어요.
6. **공장**: 각 작업에 다음에 필요한 일을 추적하고 준비되면 에이전트를 배정하는 엔드투엔드 시스템이에요.

### 네 가지 구성 요소

- **작업 서비스**: 엔지니어가 설정 파일과 Markdown 프롬프트로 워크플로를 정의해요(상태, 허용 전이, 사람이 필요한 단계). 모든 워크플로가 UI에 보여요.
- **디스패치 루프**: 다음 단계가 준비된 작업에 현재 상태의 지침으로 Codex 턴을 시작해요.
- **클라우드 Codex**: 내부 네트워크 환경에서 코드 저장소와 지표·로그·트레이스·CPU 프로파일·메모리 스냅샷에 접근하고, 서비스 ID로 돌아 권한을 제한하고 행동을 추적해요.
- **구독**: PR 리뷰 코멘트나 CI 실패, 배포 완료 같은 이벤트가 오면 작업을 다시 깨워요.

### Regression Workflow

단계는 조사 필요 → 근본 원인 확인 → 수정 제안 → 해결이에요. 에이전트는 지표가 처음 나빠진 시점을 거슬러 찾고, 비슷한 요청이 실제로 느려졌는지 원래 느린 요청이 늘었는지 비교한 뒤 배포·기능 플래그 변경과 코드를 봐요.

- **적대적 리뷰**: 초기에는 첫 그럴듯한 설명에서 멈춰 틀리는 일이 있어, 별도 Codex 세션이 진단을 반증하려 해요. 이미지 다운로드 오류를 원인으로 지목했지만 파일 위치 서비스는 이미 회복됐는데 실패가 계속된 사례에서 리뷰어가 조사를 다시 열었어요. 근본 원인 제안 100건을 사람이 검토했더니 70%가 정확했고 30%는 보완이 필요하거나 인과를 다 입증하지 못했어요.
- **수정이 더 어려워요**: 진단이 통과하면 Codex가 수정 PR을 열고 엔지니어가 머지를 결정해요. 작업 보고서에 회귀·영향·원인·수정안 요약과 지표 시계열, CPU 플레임 그래프, 트레이스가 붙어요. PR 코멘트를 남기면 에이전트가 깨어나 반영해요.
- **복구 검증**: 배포 후 기준선으로 돌아오면 해결, 일부만 회복되면 원래 건을 닫고 남은 지연은 새 작업으로, 개선이 없으면 다시 조사로 돌려요.

에이전트 수정안이 필요 이상으로 복잡하거나 새 문제를 만드는 경우도 있어 수정안에도 적대적 리뷰를 붙였고, 캐시 추가처럼 오래된 데이터 위험을 저울질해야 하는 아키텍처 결정은 서비스를 아는 엔지니어의 판단이 필요하다고 해요. 에이전트 제안과 실제 머지된 변경을 비교하는 평가·개선 루프도 만들고 있다고 해요.
