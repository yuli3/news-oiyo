### Airflow란

Apache Airflow는 워크플로를 프로그래밍 방식으로 작성하고 스케줄링하고 모니터링하는 플랫폼이에요. 워크플로를 코드로 정의하면 유지보수, 버전 관리, 테스트, 협업이 쉬워져요. 사용자는 작업(task)을 조율하는 워크플로(Dag)를 작성하고, Airflow 스케줄러가 지정된 의존성에 따라 여러 워커에서 작업을 실행해요. 풍부한 CLI로 Dag를 정교하게 다룰 수 있고, UI로 운영 중인 파이프라인을 시각화하고 진행 상황을 보며 문제를 해결할 수 있어요.

### 프로젝트가 잘 맞는 곳

- 대부분 정적이고 천천히 바뀌는 워크플로에 가장 잘 맞아요. 실행마다 Dag 구조가 비슷하면 작업 단위와 연속성이 분명해져요. 비슷한 프로젝트로 Luigi, Oozie, Azkaban이 있어요.
- 전통적 데이터 파이프라인 외에 ML 워크플로(학습, 재학습, 평가, 배포) 조율에 널리 쓰이고, 점점 **에이전트·LLM 기반 워크로드**도 조율해요. 이때 Airflow는 에이전트 자체가 아니라 AI 파이프라인의 단계(데이터 준비, 도구 호출, 모델 호출, 평가)를 엮는 역할이에요. README는 이게 새 방향이 아니라 팀들이 수년간 해 온 일이며, Airflow 레지스트리의 AI & ML 프로바이더 생태계가 커지고 있다고 말해요.
- 작업은 가급적 멱등적(같은 결과, 대상 시스템에 중복 데이터 없음)이어야 하고, 작업 간에 대량 데이터를 넘기지 않는 게 좋다고 봐요. 메타데이터는 XCom으로 주고받고, 대용량 처리 작업은 전문 외부 서비스에 맡기는 게 모범 사례예요.
- 스트리밍 솔루션은 아니지만, 스트림에서 배치로 데이터를 가져와 실시간 데이터를 처리하는 데 자주 쓰여요.

### 원칙

- **동적**: 파이프라인을 코드로 정의해 Dag를 동적으로 만들고 파라미터화해요.
- **확장 가능**: 다양한 내장 오퍼레이터가 있고 필요에 맞게 확장해요.
- **유연**: Jinja 템플릿 엔진으로 풍부하게 커스터마이즈해요.

### 요구 사항 (안정 버전 3.4.0 기준)

- Python 3.11, 3.12, 3.13, 3.14
- 플랫폼 AMD64/ARM64, Kubernetes 1.31~1.37
- PostgreSQL 14~18, MySQL 8.0·8.4·Innovation, SQLite 3.15.0 이상
- MariaDB는 테스트·권장하지 않아요. SQLite는 테스트용이라 운영 환경에선 쓰지 말라고 해요.
- POSIX 호환 OS에서 실행되고, Windows에서는 WSL2나 리눅스 컨테이너로 돌릴 수 있어요. Windows 지원 작업(#10388)은 우선순위가 높지 않아요. 운영 환경은 리눅스만 지원하며, CI와 커뮤니티 DockerHub 이미지는 Debian Bookworm을 써요.
