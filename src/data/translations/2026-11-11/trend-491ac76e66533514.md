Strands Agents 블로그 글을 "교훈" 첫머리까지 읽고 옮겼어요. 마지막 부분은 읽지 못해 partial로 표시했어요. Amazon 사내 티켓 시스템을 맡은 엔지니어 Carr와 Mehul이 직접 쓴 사례예요.

### 배경: Sonnet 4.6으로 티켓에 라벨 붙이기

Amazon과 AWS 팀은 세계 최대급 사내 티켓 시스템에서 Claude Sonnet 4.6으로 티켓에 라벨을 붙여 왔어요. 티켓은 고객 에스컬레이션, 용량 요청, 자동 알람, 보안 발견 사항 등 무엇이든 될 수 있고, 20개 카테고리 중 하나로 분류해야 했어요. 에이전트는 티켓마다 긴 시스템 프롬프트를 받아 JSON을 만들고, 정해진 라벨 목록을 놓고 추론했어요.

### 결정 모델로 LLM의 일을 대신하기

결정 모델은 텍스트를 만들지 못해요. 상태와 질문, 선택지를 받으면 선택지마다 확률과 확신도(confidence)를 돌려줘요. 글쓴이들은 이 방식이 티켓 라벨링에 딱 맞는다고 봤어요. 상태는 티켓이고, 선택지는 라벨 목록이에요.

- 처음엔 Strands Decider 2B로 시작했지만, 테스트 세트에서 Gemma 4 기반 E4B 빌드가 확실히 나아서 바꿨어요.
- 라벨을 적용하기 전에 필요한 확신도 기준을 조정했고, 별도 티켓 세트에서 E4B가 운영 중인 Sonnet을 이겼어요.
- SageMaker `ml.g5.xlarge`(A10G 1장, 24GB)에서 돌렸고 모델은 약 19GiB를 썼으며 요청 하나에 약 640ms가 걸렸어요.
- 경로는 SQS → Lambda → SageMaker AI Endpoint이고, AppConfig가 스위치를, CloudWatch가 로그·지표·알람을 맡아요. 스택은 CDK로 Beta·Gamma·Prod 단계를 두었어요.

### 같은 티켓에 두 모델을 나란히

스위치를 한 번에 바꾸지 않고, Lambda가 메시지마다 AppConfig의 세 가지 설정을 읽게 했어요.

- `BEDROCK`: Sonnet만 라벨을 붙여요.
- `DUAL`: 두 모델을 병렬로 부르고, Sonnet 결과를 적용하면서 Decider 결과와 비교해요.
- `DECIDER`: Decider만 라벨을 붙이고 Bedrock은 부르지 않아요.

### 측정 결과

- 호출당 평균 시간: 4,215ms → 897ms (78% 개선)
- 티켓당 총 토큰: 6,724 → 2,010 (70% 감소), 출력 토큰은 170 → 1

토큰이 준 이유는 두 가지예요. Decider는 JSON 대신 선택 하나만 출력하고, 프롬프트도 훨씬 짧아요. 운영 라벨 설명만으로도 Decider의 4,096토큰 창을 넘어서, 20개 라벨을 한두 문장짜리 기준으로 다시 쓰고 "none" 선택지를 더해 하나의 선택형 질문으로 보냈어요. 긴 티켓은 오래된 댓글부터 잘라서 맞췄어요. Sonnet을 끈 날 Lambda 평균 실행 시간은 74% 줄었어요.

### 비용

us-east-1 온디맨드 공시 가격 기준으로 Sonnet 4.6은 티켓당 0.0222달러, 100만 건당 약 2만 2,200달러예요. Decider E4B는 인스턴스시간당 1.408달러이고, 한 인스턴스가 시간당 약 5,600건을 처리할 수 있어 완전 가동이면 100만 건당 250달러예요. 버스트 여유를 두면 실제로는 약 500달러로, 약 44배 싸고 98% 줄어든 셈이에요. Lambda 비용은 빠진 수치예요.

> 놀랐던 점: JSON 키 순서만 바꿔도 출력 확률이 최대 0.19까지 움직였어요. 지금은 모든 요청을 키를 정렬해서 보내요.

### 교훈

이 방식이 통한 건 작업이 알려진 목록에서 고르는 닫힌 선택이고, 양이 많고, 기존 경로의 지연이 중요했기 때문이라고 글쓴이들은 정리해요.
