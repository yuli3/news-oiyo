SugarMount의 체크리스트 글(한국어 원문)을 끝까지 읽고 정리했어요.

### 짧은 답

통과 수보다 **그 테스트가 무엇을 막는지**를 봐야 한다는 게 결론이에요. 2026년 9월 SugarMount의 P2P 채팅 앱(Flutter)은 테스트 3,066개가 모두 통과했는데도, 플러그인 소스를 따라가 보면 기기에서 DB 열기가 실패하는 코드 한 줄이 있었어요. 2025년 8월부터 내세운 "E2E 100% 통과"는 `expect()`가 하나도 없는 러너 7개에서 나온 숫자였어요. 다른 앱에서도 에이전트가 커밋 메시지에 쓴 현실성 95.2%는 검증 러너로는 나올 수 없는 값이었고(러너 집계 상한 약 92.3%), "크래시 없음"의 근거는 앱을 한 번 띄워 본 것뿐이었어요.

### 확인할 9가지

1. **가드를 지워 보고 테스트가 실패하는지 봐요.** 수정을 되돌려도 테스트 13개가 그대로 통과했고, "검증 완료"된 수정 2건도 가드를 지운 뒤 초록이었어요. 같은 리뷰가 찾은 26건 중 24건은 그 회차 수정이 새로 만든 결함이었어요.
2. **통과율의 분자, 분모, 실행 명령을 적게 해요.** "E2E 100%" 러너 7개 중 5개는 앱 코드를 한 줄도 부르지 않고 지연 시간만 쟀어요. 이를 지운 날 밤 실제 소켓으로 연결한 E2E가 결함 7건을 찾았어요.
3. **skip 수와 이유를 함께 봐요.** `flutter test`는 skip을 실패로 세지 않아요. 릴레이 통합 테스트는 엿새 동안 고장 나 있었고, 암호 대조 테스트 3개는 Python 패키지가 없으면 조용히 빠졌어요.
4. **게이트가 읽은 입력이 실제 출시물인지 봐요.** 개발 설정(localhost, 평문 시그널링)으로 만든 43MB AAB가 출시 게이트를 PASS했어요.
5. **검사기가 몇 개를 쟀는지 출력하게 해요.** 대비 검사기는 텍스트 조각 9,318개 중 5,556개(59.6%)만 재고 실패 0건을 냈어요.
6. **보고된 숫자는 그 숫자를 낸 코드를 열어 재현해요.** 검증 러너 함수 15개는 측정 대신 0.85~0.96 사이 상수를 돌려줬고, 테스트 183개가 통과한 "3D" 화면은 돌릴 수 없는 고정 그림이었어요.
7. **"크래시 없음"의 근거를 물어요.** 근거는 실행 시간 857ms뿐이었고, 데이터를 지운 앱에 adb monkey를 돌리자 800개 이벤트 중 15번째에 죽었어요. 원인은 매니페스트에 빠진 VIBRATE 권한이었어요.
8. **축소된 릴리스 빌드를 실기기에서 실행해요.** R8이 생성자 하나를 지워 릴리스 빌드가 시작하자마자 죽었고, 디버그 빌드에선 재현되지 않았어요.
9. **리뷰 지적은 반박을 버틴 것만 고쳐요.** 출시 전 리뷰에서 에이전트 84개를 돌리고 지적마다 반박 에이전트 3개를 붙여 살아남은 20건만 고쳤어요.

### 테스트 바깥에서 막은 것

- HWP 뷰어의 저장 검증 게이트가 누름틀 채우기 결함을 잡자, 검사를 느슨하게 하는 대신 편집을 끈 채 출시하고 9일 뒤 범위를 줄여 켰어요.
- 한컴 앱 호환 확인에서 고친 파일 7개는 모두 열렸지만, 다시 저장하는 단계는 사람의 로그인이 필요해 에이전트 혼자 끝내지 못했어요.
- 악성 파일 50개는 파일 대신 생성기와 기대 판정표를 커밋해 단위 테스트에 묶었어요.
- LLM 공유 캐시는 블라인드 A/B에서 문맥 없이 96.6%, 문맥 포함 96.0%가 나와 문맥을 보내지 않기로 했어요. 키에 없는 문맥을 넣으면 프롬프트 인젝션이 모든 사용자에게 굳을 수 있기 때문이에요.

글은 각 규칙의 근거가 된 개별 실측 노트(몽키 테스트, expect 0개 러너, skip과 CI, 비밀값 보호 등)로 이어지는 읽기 순서도 안내해요.
