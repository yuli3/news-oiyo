Specify 랜딩 페이지의 앞부분(소개, 데모, 문제 정의)을 읽고 옮겼어요. 아래쪽 활용 사례와 요금 부분은 다 읽지 못했어요.

### "어제 받아들인 코드, 오늘 설명할 수 있나요?"

Specify는 "구현은 에이전트에게 맡기고, 당신은 아키텍트가 되라"고 말해요. 다이어그램으로 구조를 보고, 기능 문서로 의도를 확인하는 도구예요. 저장소 하나로 시작할 수 있고 개인 무료 플랜이 있어요(카드 불필요).

### 데모에서 보여 주는 흐름

페이지 데모는 payments-api 저장소를 예로 들어요. 사용자가 "환불도 기존 ApiClient를 쓰게 하고 새 클라이언트는 지워 줘"라고 하면, Specify가 다이어그램과 저장소를 확인하고 개선 문서를 써요. 그다음 Claude Code에서 "Specify 개선 문서대로 고쳐 줘"라고 하면 Claude Code가 Specify MCP로 문서를 읽고 수정 커밋을 만들고, 다이어그램이 다음 커밋에서 갱신돼요. 정리하면 세 단계예요.

1. 푸시할 때마다 다시 그려요.
2. 쉬운 말로 검토해요.
3. 에이전트가 개선 문서를 보고 고쳐요.

### 풀려는 문제: "돌아간다"와 "맞다"는 달라요

- **커밋이 읽는 속도보다 빨리 쌓여요.** 하루에도 수십 번 바뀌는 코드를 의도한 아키텍처와 데이터 흐름을 따르는지 확인하지 않고 받아들이게 돼요.
- **에이전트는 기능을 만들지 구조를 만들지 않아요.** 전체 아키텍처를 지키는 건 여전히 사람 몫이에요.
- **아무도 설명 못 하는 코드가 배포돼요.** 테스트가 통과하면 머지되고, 무엇을 왜 그렇게 만들었는지 말하기 전에 프로덕션에 가요.

페이지는 Stack Overflow 2025 개발자 설문에서 개발자 66%가 "거의 맞지만 완전히 맞지는 않은 AI 결과"를 가장 큰 불만으로 꼽았다는 수치도 인용해요.
