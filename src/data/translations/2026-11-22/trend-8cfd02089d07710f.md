George Xenos와 Sotiris Giannopoulos가 2026년 11월에 쓴 글 "Programming in the Machine Code Space"를 끝까지 읽고 정리했어요.

### 한 줄 요약

디스어셈블러도 컴파일러도 없이 hex dump만 받은 GPT-6.1 Sol이 실행 파일을 바이트 단위로 읽고 쓸 수 있었다는 실험이에요. 저자들은 이를 LLM이 바이너리로 직접 프로그래밍할 수 있다는 초기 신호로 봐요.

### 실험 설정

- 모델: Codex CLI 0.166.0을 통한 `gpt-6.1-sol`(effort high).
- 입력: 프롬프트에 붙여 넣은 `xxd` hex dump. 1바이트당 약 2.4토큰이 들어요. 실험 3만 hex 없이 글로 쓴 명세를 받아요.
- 도구 없음: 로컬 릴레이가 모든 요청에서 도구를 빼고, 매 턴 이벤트 스트림을 감사했어요.
- 한 번의 응답: 피드백도 재시도도 없어요.
- 채점: 결과물과 GCC 참조 빌드를 모든 테스트 케이스에서 돌려 stdout과 종료 코드가 바이트 단위로 같아야 통과예요(Apple Silicon의 `qemu-x86_64`에서 실행).

### 실험 1: 바이트만 보고 프로그램 이해하기

직접 만든 프로그램 세 개(wordcount, AES 도구, 은행 원장)와 FreeBSD의 `ministat`을 줬고, 네 개 모두 무엇인지 맞혔어요. 가장 어려운 `ministat`은 `-O3`로 빌드해 musl에 정적 링크하고 strip한 뒤 문자열까지 숨겼는데도 디코딩 루프를 찾아 옵션 여덟 개를 모두 설명했어요. 게다가 t-table을 64비트 실수로 읽다가 99.5% 신뢰 옵션이 실제로는 약 99.8% 임곗값을 쓴다는 **실제 업스트림 버그**까지 찾았어요. 저자들은 원본 소스에서 이 버그를 확인했어요.

### 실험 2: 바이트를 고쳐 기능 추가하기

- wordcount: 가장 긴 줄 길이를 넷째 숫자로 출력, 74바이트(1.4%) 변경
- AES 도구: 복호화 `dec` 명령 추가, 544바이트(5.9%) 변경
- 은행 원장: 계좌 간 `transfer` 명령 추가, 379바이트(4.3%) 변경

세 프로그램 모두 기존 동작, 새 기능, 긴 입력 테스트를 전부 통과했어요. 방식은 사람이 바이너리를 패치하는 것과 같아요. 패딩을 찾아 세그먼트 헤더를 고쳐 실행 가능하게 만들고, 거기에 새 코드를 쓴 뒤 기존 명령어를 그 코드로 가는 호출로 덮어써요.

### 실험 3: 명세만 보고 실행 파일 쓰기

어셈블러 없이 헤더까지 모든 바이트를 응답으로 내야 했는데, 세 파일 모두 실행됐고 모든 케이스에서 참조와 같았어요. wordcount는 391바이트(GCC 빌드 5,432바이트), AES 도구는 4,144바이트, 원장은 3,584바이트였어요. AES 조회 테이블은 표준과 정확히 일치했어요. 확장은 새로 쓰기보다 출력 토큰이 1.8~3.7배 적게 들었어요.

### 실험 4·5: 실제 악성코드 분석

4,608바이트짜리 PE32+ 샘플(보이는 import는 `Sleep`뿐)을 악성이라는 힌트 없이 줬어요. 211초 만에 "메모리에서 기계어를 내려받아 실행한다"고 결론 내렸고, 하드코딩된 서버 `165.154.205.34:443`을 짚었어요. 공개 VMRay 동적 분석과 비교하니 주소와 요청 URL, 다운로드가 일치했어요. 다만 10초 재시도와 XOR 키(0x99) 자체는 샌드박스로 확인되지 않았고, 표본은 하나뿐이라고 밝혔어요. 오픈 웨이트 모델인 DeepSeek V4.1 Flash(다른 하네스 opencode)도 같은 샘플에서 같은 결론에 이르렀어요.

### 한계와 시사점

- 맥락 길이가 가장 큰 한계예요. 67KB 바이너리가 약 16만 3,000토큰이었고, 10MB 프로그램이면 약 2,400만 토큰이 필요해요. Recursive Language Model 방식 하네스를 대안으로 제시해요.
- 저자들은 역공학과 악성코드 분석에서 디스어셈블·디컴파일 단계가 LLM에게는 선택 사항이 될 수 있다고 봐요. 다만 작은 프로그램에 대한 초기 결과라는 점을 분명히 해요.
