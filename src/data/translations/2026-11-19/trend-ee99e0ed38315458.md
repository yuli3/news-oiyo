오픈AI 엔지니어링 글(2026년 11월 18일, 기술 직원 마이클 볼린)을 읽었어요. 글은 맥·리눅스·윈도우에서 제한이 어떻게 강제되는지로 끝난다고 안내하지만, 이 수집은 ‘네트워크 프록시’ 절의 “The proxy checks each request ag”에서 잘려 그 뒤 운영체제별 구현은 옮기지 않았어요.

오픈AI는 에이전트 보호에 심층 방어를 쓰고, 학습과 정렬에 더해 코덱스 하니스에 기능을 넣는다고 해요. 코덱스가 자주, 그리고 위험할 수 있게 하는 일 중 하나가 사용자 컴퓨터에서 명령을 실행하는 것이라, 코덱스 샌드박스를 만들어 파일 시스템과 네트워크 한도 안에서 기존 환경을 쓰게 했다고 해요. 샌드박스는 실행 중 프로그램이 접근할 수 있는 범위를 제한하고, 사용자는 권한 프로필로 세션의 파일 시스템·네트워크 제한을 정해요. 사진 정리라면 ~/Pictures 읽기·수정은 허용하고 업로드를 막으려 네트워크를 차단할 수 있고, 코드 리뷰라면 온라인 문서는 허용하되 소스 파일은 읽기 전용으로 둘 수 있다고 해요.

기본값은 의미 있는 일은 하면서도 보수적으로 둔다고 해요. 깃 저장소를 작업 공간 루트로 하는 내장 :workspace 프로필은, 작업 공간 안 쓰기는 허용하되 .git과 .codex는 읽기 전용으로 남겨 소스 편집은 매번 허가 없이 하면서 .codex/config.toml이나 .git/hooks는 직접 못 바꾸게 해요. 파일 시스템 읽기는 운영체제 권한 안에서 넓게 허용하는데, 컴파일러와 빌드 도구가 저장소 밖 SDK와 설정에 의존하기 때문이에요. 대가는 다른 곳의 API 키가 든 설정 파일도 읽힐 수 있다는 점이에요. 네트워크는 꺼서 외부 업로드와 데이터 반출을 막지만, 의존성 다운로드 같은 정당한 작업도 막아요. 그래도 해로운 행동은 가능해요. 예로 에이전트가 node_modules/prettier에 악성 코드를 넣으면 git status에 안 보일 수 있고, 편집기가 저장 시 그 복사본을 실행하면 샌드박스 밖에서 코드가 돌 수 있다고 해요. 그래서 샌드박스가 접근을 제한하고, 학습과 정렬이 그 접근을 사용자 의도에 맞게 쓰도록 돕는 심층 방어를 쓴다고 해요. 기업 환경 안내는 코덱스 보안 쿡북을 보라고 해요.

가상머신이나 컨테이너로 계산을 다른 환경으로 옮기지 않고, 각 플랫폼의 샌드박스 기능으로 사용자 환경에서 명령을 제한한다고 해요. 노트북이 자주 바뀌는 개발 환경이고, 도커로 재현하기 번거로우며 호스트 도구에 의존하는 작업도 있기 때문이에요. 맥에서 iOS 앱을 개발할 때 도커 안이면 네이티브 맥 실행 파일로 된 빌드 도구와 아이폰 시뮬레이터를 쓸 수 없고, 호스트에 맡기면 그 작업은 컨테이너 샌드박스 밖이라 따로 제한해야 한다고 해요. 하니스는 맥·윈도우·리눅스에 공통 API를 제공하고, 명령과 권한 프로필을 받으며, 제한된 네트워크를 허용하면 호출자가 네트워크 프록시를 공급해야 한다고 해요. 자식 프로세스는 부모의 제한을 상속해, 원래 프로세스보다 오래 사는 자손에도 적용된다고 해요.

코덱스 하니스는 모델이 만든 도구 호출을 실행하고, 코딩에서 가장 흔한 것은 대화형 셸처럼 명령을 돌리는 셸 도구예요. 글은 한 번 실행하는 exec_command를 예로, 샌드박스가 없으면 subprocess.Popen으로 돌리고, 있으면 spawn_command_under_sandbox에 프로필과 필요 시 프록시를 넣는다고 보여 줘요. 모델이 명령마다 권한을 요청할 수 있지만 하니스가 사용자 설정에 따라 줄지 말지 정해요. use_default는 그 턴의 기본 설정, with_additional_permissions는 샌드박스 안에서 접근을 넓히기, require_escalated는 샌드박스 밖 실행이고 사용자에게 묻거나 auto-review로 보낼 수 있다고 해요. 셸 도구가 주요 사용자이고, 로컬 파일 읽기·수정도 같은 인프라를 재사용한다고 해요.

이름 있는 권한 프로필은 프로젝트 간에 재사용할 수 있고, config.toml의 [permissions]에 정의해요. 예로 dev는 :workspace를 확장해 ~/build-cache 쓰기를 더하고, 작업 공간의 .devcontainer와 .vscode는 읽기, **/*.env와 secrets는 거부해요. 파일 시스템 항목은 read, write, deny예요. :workspace_roots는 작업 공간 루트에 상대적인 규칙이고, CLI는 작업 디렉터리, 챗GPT 데스크톱은 프로젝트 소스 폴더를 루트로 쓴다고 해요. :workspace에서 상속되는 읽기 전용에는 .agents, .aws, .codex, .git이 있어요.

네트워크는 전부 차단(:workspace 기본), 전체 직접 접근(:danger-full-access 기본), 프록시로 프로필에 따라 통과를 정하는 세 갈래예요. 도메인 규칙은 정확한 이름과 와일드카드를 쓰고, deny가 allow보다 우선하며, 다른 도메인은 승인이나 차단이 필요하다고 해요. 설정은 여러 config.toml을 합치고, 표는 재귀적으로 합치며 배열은 통째로 바뀐다고 해요. 관리자는 requirements.toml로 managed requirements를 공급해, 예를 들어 기본을 :read-only로 두고 :danger-full-access를 금지할 수 있으며, 클라우드 요구가 /etc/codex/requirements.toml보다 앞선다고 해요.

CLI의 codex sandbox 명령은 에이전트 세션 없이 같은 프로필로 임의 명령을 시험할 수 있어요. 글의 예에서 dev 프로필은 이미 있는 .vscode에 악성 포매터 경로를 쓰려는 명령을 맥에서 “Operation not permitted”로 막아요. 표준 입출력 MCP 서버를 켜는 명령은 하니스가 샌드박스하지 않는데, 필요한 파일과 네트워크를 짐작하기 어렵기 때문이에요. 그래서 @modelcontextprotocol/server-memory 예를 들며, 원래 npx는 사용자와 같은 권한이라 과도하고, memory-mcp 프로필로 읽기는 넓게, ~/.npm과 ~/mcp-data만 쓰기, 네트워크는 끈 채 `codex sandbox`로 npx를 감싸라고 해요. 구현 절은 권한 프로필을 운영체제 제한으로 바꾸고, 프록시의 요청 처리와 정책 논리는 세 운영체제에서 공유되며 설정과 샌드박스 연동은 OS마다 다르다고 한 뒤, 이 수집에서는 끊겨요.
