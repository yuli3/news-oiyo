Jina Yoon의 PostHog 뉴스레터 글(2026년 11월 9일) 본문을 끝까지 읽었어요. 아래 댓글과 채용·추천 글 목록은 본문이 아니어서 옮기지 않았어요. 글쓴이는 이 글이 두 달이면 구식이 될 것이라고 적어요.

### 결정 모델이란

LLM은 간단한 질문에도 “상황에 따라 다르다”는 긴 산문을 돌리는 경향이 있어서, 더 단순한 작업에는 Jev 같은 결정 모델을 즐겨 쓴다고 해요. 구조화된 질문을 하면 타입이 있는 답과 확률이 나와요. 예시로 Noul “고슴도치는 포유류인가?” → Yes, 0.99, Choice “어느 동물 과인가?” → Mammal, 0.99, Score “보전 상태는?” → Least Concern, 0.77을 들어요. 보정된 모델에서는 점수 0.8인 답이 약 80% 맞고, 0.5는 동전 던지기와 같다고 해요. PostHog에서 실험하다 여러 용도가 프로덕션에 올라갔다고 해요.

### 1. 비싼 LLM 호출을 걸러요

결정 모델은 프런티어 모델보다 최대 444.6배 싸고 193.6배 빠르다고 하며, 각주는 TypeSafe AI를 출처로 들어요. 그래서 비싼 LLM을 부를지부터 검사하는 데 쓸 수 있어요.

세션 녹화를 보고 요약하는 Replay Vision에서 개인정보를 지우는 파이프라인이 그래요. 각 세션 요약에 결정 모델이 예/아니요 질문 두 개를 던져요. “이 요약이 실제 사람 이름을 말하나?”, “연락처나 신분증을 보여 주나?”처럼 좁힌 질문이, 질문 하나로 할 때보다 거짓 표시를 약 10분의 1로 줄였다고 해요. 둘 중 하나라도 0.4 이상이면 Gemini가 개인정보 없이 요약을 다시 쓰고 다시 검사하고, 아니면 깨끗하다고 보고 통과해요. 프로덕션에서는 98.7%가 LLM 호출을 완전히 건너뛴다고 해요. 결정 모델이 없으면 프롬프트와 정규식을 계속 만지거나, 1%를 잡으려고 모든 요약을 Gemini에 보내야 한다고 해요.

다만 실수도 해요. 확률 0.85도 검사 1,000건당 약 150건이 틀릴 수 있으니 거짓 양성과 거짓 음성을 미리 계획하라고 해요. PII 예에서는 거짓 양성은 LLM을 한 번 더 부르는 비용이고, 거짓 음성은 개인정보를 깨끗한 것으로 저장하므로 임계값을 0.4로 낮게 두었어요. 거짓 양성이 더 비싼 실수일 때는 임계값을 높여요. Slack의 PostHog 봇이 태그 없이 질문에 답하게 바꿨을 때는, 채널의 모든 메시지가 (1) 정보를 묻는 것인지, (2) PostHog가 답할 수 있는지를 보고, 둘 다 0.85 이상일 때만 진행해요.

### 2–4. 라우터, 표면 검사, 과한 LLM 대체

같은 Slack 봇은 결정 모델을 모델 라우터로도 써요. 태그를 받으면 먼저 특정 모델을 지정했는지 보고, 아니면 “첫 시도에 과제를 맞출 가능성이 가장 높은 가장 싼 옵션을 고르라. 실패한 실행이 더 똑똑한 옵션보다 비용이 크다”는 선택 질문으로 목록에서 고른다고 해요. 각 옵션에는 짧은 적성 설명이 있고, 예로 GPT Luna는 “가볍고 매우 싼 모델. 짧은 답, 조회, 요약, 아주 작은 수정에 좋다”고 적혀 있어요. 결정 모델은 요청을 각 옵션 텍스트에 대해 채점해요.

작업·모델·제공자마다 임계값이 달라요. Error Tracking에서 비슷한 로그를 자동 병합하는 실험에서는 같은 모델 v1과 v2 사이에 임계값이 바뀌어, PostHog 프로젝트마다 설정할 수 있게 하고, 손으로 라벨한 데이터로 다시 보정하는 동안 판정기를 섀도 모드로 뒀다고 해요. 성장팀의 Fernando가 일찍 모델에 묶이지 않는 인터페이스를 밀어, 지금은 자체 호스팅 모델을 포함해 바꾸고 시험하는 내부 AI 게이트웨이가 있다고 해요.

더 많은 맥락이나 추론 사슬이 필요하면 LLM이 낫지만, 입력을 납작하게 전처리해 표면만 보면 되게 만들면 결정 모델을 쓸 수 있어요. Replay Vision에서 “온보딩 마찰” 같은 테마 검색은 임베딩 거리 때문에 뜻밖의 결과가 섞일 수 있어요. “사용자 검색과 맞는 요약이 있는 세션 상위 10개를 순위를 매겨라”는 결정 모델에 맡기기엔 너무 복잡해서, 먼저 임베딩으로 후보 목록을 만든 뒤 “이 요약이 검색이 찾는 세션을 설명하나?”만 보게 하고 그 확률로 다시 순위를 매겨요. 시험 질의 20개에서 순위 품질이 약 25% 좋아졌다고 해요.

다단계 추론은 피하라고 해요. 임베딩이 준비되기 전 Highlights 피드에 “볼 가치가 있나?”, “있다면 이유는?”(화면에 오류, 느리거나 멈춤, 사용자 혼란, 포기 등)을 순서대로 물어 봤더니, 시간당 작업이 세션 최대 32개, 요청당 12–38k 토큰의 큰 요청을 보내 모델 서버를 메우고 다른 제품 호출을 몇 시간 막았다고 해요. 기술적으로는 이을 수 있지만 운영상 가치가 없으니, 다단계는 LLM에 두거나 결정 모델이 보기 전에 무거운 일을 하라고 해요.

LLM이 과한 일에도 쓸 수 있어요. SQL 질의의 더 똑똑한 차트 선택이 예예요. 예전에는 날짜+숫자+여러 행이면 선 차트, 텍스트 열 둘 이상과 숫자면 히트맵, 숫자 열이 있으면 막대처럼 결정론적 규칙이었어요. 지금은 조직이 동의하면 SQL 자체와 결과의 처음 세 행을 결정 모델이 보고 더 나은 차트를 제안해요. 브라우저별 페이지뷰 질의에서 원래 규칙은 기본 집계 선 차트를 골랐고, Jev는 브라우저로 나눈 막대를 골랐다고 해요.

더 열린 일은 여전히 LLM에 두라고 해요. 내부 PR 리뷰 에이전트 소견을 “개발자가 볼 만한 변경인가”에 가까운 noul 질문 다섯 개로 순위를 매겨 봤더니 AUC 0.52로 결론이 안 났다고 해요. LLM이라면 맥락을 더 넣겠지만 Jev는 큰 요청을 다루지 못하고, 긴 맥락 모드는 더 느리고 정확도도 떨어진다고 해요. 각주에 따르면 Jev는 기본적으로 요청당 64k 토큰, 질문당 32k이고, TypeSafe가 둘 다 262k로 올리는 선택 헤더를 추가했지만 긴 맥락 모드는 더 느리고 덜 정확하다고 문서가 경고해요. 사내 AI 연구팀이 만든 하이브리드 결정 모델 Jeeves는 확신이 없을 때 먼저 추론한 뒤 결정하며, 지금은 모델을 지정하지 않은 PostHog의 모든 결정 호출 기본값이고, 다른 개발자의 비슷한 변형으로 Kev를 들어요. 결정 모델은 언어 모델에는 너무 단순하고 정규식에는 너무 모호한 입력의 평가자로 쓰라는 것이 결론이에요.
