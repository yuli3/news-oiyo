Kernel 블로그 글(2026년 11월)을 끝까지 읽었어요. 글 상단은 해커뉴스 토론이 238포인트, 댓글 125개라고 안내해요. 차트에 그려진 정확한 달러·초 숫자는 이미지라서, 본문에 적힌 비율과 시간만 옮겼어요.

### 무엇이 느렸나

비공개 평가 중 하나에서 Carbon이, Opus와 Astra는 보통 몇 분이면 끝내는 일을 거의 한 시간에 가깝게 쓰는 것을 봤다고 해요. 시간·비용 차트는 왼쪽이 더 빠르고 아래가 더 싸며, API 정가와 월 200달러 요금제를 전부 쓸 때를 함께 보여 주고, Carbon은 도입 할인 이후 요금, 구독 보조율은 Opus 40배, Astra 13배, Carbon 3배, Hydrogen 17배를 썼다고 해요. 다른 사용자도 X 등에서 실사용이 너무 느리다고 말했고, 한 비교는 Carbon low 22분 21초, Opus 5.5 high 9분 33초였어요.

과제는 버그가 고쳐지기 직전 코드베이스와, 증상만 적은 보고서를 주고, 관련 없는 변경 없이 원인을 찾고 고치는 일이에요. 어려움의 상당 부분은 생 지능보다 공학적 판단, 즉 증상을 올바른 코드 경로로 추적하고, 경쟁 설명을 배제하고, 수정을 올바른 자리에 두고, 언제 멈출지를 아는 데 있다고 해요.

### 느린 추론인가, 일을 더 하나

먼저 가려낸 것은 추론 속도예요. 제공자 대기, 네트워크 지연, 프롬프트 처리와 생성 속도가 각 스텝이 걸리는 시간을 정해요. 이 느린 추론이 Carbon의 추가 시간 중 Astra 대비 16–30%, Opus 대비 45–49%를 설명하고, 나머지는 더 긴 궤적, 즉 과제당 일을 더 하는 데서 온다고 해요.

버그당 평균으로 Carbon은 Astra보다 스텝이 약 7배, 파일을 읽거나 명령을 실행하는 같은 액션이 11배, 쓰는 양은 7배예요. 매 스텝이 점점 길어지는 대화를 다시 보내므로 입력으로 처리하는 양은 16배가 넘는다고 해요.

더 단순한 설명도 먼저 배제했어요. 하니스를 바꾸려고 Carbon을 opencode와 mini-SWE-agent 안에서도 돌렸지만 의미 있는 차이는 없었어요. 노력 단계가 제공자마다 표준화되어 있지 않아 Carbon의 "high"가 다른 모델의 최대 설정에 더 가까울 수 있고, 더 공정한 비교는 Carbon low일 수 있지만, low에서는 수정을 전혀 내지 못하는 경우가 많고, 이미 읽은 코드를 다시 읽으며 맴돌았다고 해요.

### 추적에서 본 것

Astra와 Carbon 실행의 모든 스텝을 목적별로 라벨해 세어 보니, Carbon 스텝의 절반이 티켓이 묻지 않은 일로 갔어요. 원인을 찾은 뒤에도 관련 경로를 넓혀 검색하고 수정이 건드릴 필요 없는 코드를 감사했으며, 티켓의 사실이 이미 배제한 경우를 막으려고 코드를 더 단단히 했다고 해요. 이미 읽은 코드를 다시 읽은 스텝 20개는 이 집계에서 빼고 다음 절에서 다뤄요.

표본 시행에서 두 모델 모두 원인을 일찍 찾았어요. Astra는 1분 안, Carbon은 약 6분. Astra는 그로부터 3분 뒤에 수정을 썼고, Carbon은 이후 25분 동안 코드를 쓰지 않았어요. 원인을 알고도 계속했는지, 확신이 없어서인지 가리려고, 수정된 하니스에서 다섯 턴마다 “이미 수정할 만큼 충분한가?”라는 같은 점검을 자동으로 넣었어요. 점검이 있으면 37분 대신 28분에 끝났고, 원인을 말한 뒤 편집까지 기다림이 25분에서 약 10분으로 줄었어요. 그래서 느림은 아는 것이 아니라 행동 방식에서 오는 것으로 보인다고 해요.

수정에 필요한 스텝 안에서도, 스텝마다 해내는 일이 적고 이미 본 코드를 다시 읽었어요. Astra는 스텝당 도구 호출이 두 번이 넘고 종종 여러 파일을 한꺼번에 읽었지만, Carbon은 약 한 번, 보통 파일 하나였어요. 다시 읽은 줄은 Carbon 39%, Astra 7%였어요. 이 두 가지 “기계적” 비효율이 초과 실행 시간의 대략 25%를 차지한다고 추정해요.

결론으로 어려운 버그 수정에서 Carbon이 거의 한 시간, Opus와 Astra가 몇 분이 걸린 차이를 셋으로 나눠요. 느린 추론(Astra 대비 16–30%, Opus 대비 약 절반), 티켓이 묻지 않은 불필요한 일(스텝의 약 절반), 스텝당 도구 호출이 적고 재읽기가 잦은 기계적 비효율(이것만 고쳐도 실행 시간이 대략 4분의 1 줄 것으로 추정)이에요.
