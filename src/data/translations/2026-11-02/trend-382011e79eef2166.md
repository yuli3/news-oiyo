GitHub의 team-solve 예제 README 전체를 읽고 옮겼어요. 제목의 "능가" 주장은 README가 직접 단 한계와 함께 봐야 해요.

### 무엇인가

**team-solve**는 작은 모델 다섯이 프로그래밍 문제를 함께 푸는 워크플로예요. 플래너, 아이디어 담당 둘, 솔버, 매니저에 수리 담당이 붙어요. 각자 **새 컨텍스트**에서 시작해 **디스크의 파일로만** 소통하고, 성공 여부는 샘플을 실행하는 스크립트가 정해요. 논문 GVS5H(Lee, 2026)의 방법을 Memdoor 워크플로로 옮긴 것으로, YAML 파일 8개이고 코드도 모델 이름도 없어요.

### 결과

저자 하네스와 같은 모델 **Qwen3.8-27B**, 같은 프롬프트·루프·128K 답변 상한으로, 저자들의 LiveCodeBench Hard 목록 첫 10문제를 문제당 5번씩 풀고 숨은 테스트 전부로 채점했어요.

| | 이 워크플로 | 저자 하네스 | Fable 5 단일 호출 |
|---|---|---|---|
| 평균(10점 만점) | 9.8 | 9.6 | 8.0 |

실행당 중앙값 40분, 0.39달러였고 50회에 35.79달러 들었어요.

### 이 결과가 보여 주지 않는 것

- 저자들의 100문제가 아니라 **10문제 × 5회**예요. 9.8과 9.6은 이 표본에선 노이즈 범위라 주장은 **저자 하네스와 동등**하다는 거예요.
- 문제는 2025년 봄 대회라 모델이 학습 중 봤을 수 있어요. **오염 가능성**은 어느 열도 배제할 수 없어요.
- Fable 5 열은 저자 파일의 문제당 단일 호출이고 이 하네스로 돌리지 않았어요. 전체 100문제 기준 저자 하네스 92.4, Fable 90.4예요.
- 루프는 공개 샘플만 보고 점수는 숨은 테스트예요. 모델은 로컬이 아니라 OpenRouter에서 돌렸어요.
- 놓친 한 문제는 매니저가 틀린 반례를 지어내 팀이 맞는 프로그램을 다시 쓴 경우였어요.

### 실행과 구조

`memdoor connect openrouter`(또는 anthropic, openai, gemini, local 등) 후 예제를 `~/.memdoor/workflows/`에 복사하고 `memdoor workflow run team-solve --wait`로 돌려요. 로컬 Ollama는 기본 4K가 아니라 32K 창이 필요해요. 흐름은 plan → ideate-a/ideate-b(병렬) → solve → test → review → repair → verify이고, 모든 프롬프트에 "새 컨텍스트, 파일을 읽고 대화에 기대지 말 것"이 들어가요. 논문은 이 장부(ledger) 규율이 성능 향상의 이유라고 봐요.
