원문(Medium, 15분 분량)의 앞부분(약 3,600자, 세 번째 질문 초반까지)을 읽고 정리했어요. 원문이 한국어라 번역이 아니라 요약·정리예요. 네 번째·다섯 번째 질문은 반영하지 않았어요.

### 출발점

필자는 AI를 쓰면서 **사람에게 일을 맡길 때와 닮은 점이 많다**고 느꼈대요. 왜 하는지 알아야 판단할 수 있고, 담당 범위가 분명해야 독립적으로 일하며, 피드백과 경험이 쌓여야 더 많이 맡길 수 있어요. 구현이 빨라질수록 무엇을 만들지, 어떤 구조에서 일할지, 결과를 어떻게 확인할지, 언제 사람이 개입할지가 더 중요해졌대요. 그래서 방향 판단 → 독립 실행 → 결과 확인 → 신뢰에 따른 위임 확대 → 배움 연결의 다섯 질문으로 묶었어요.

### 1. 무엇을 위해 이 일을 하는가?

- 상위 이유가 있어야 작업 중에도 "아직 필요한가, 더 나은 방법이 있나, 안 해도 되나"를 다시 판단할 수 있어요. 예컨대 테스트 자동화 플랫폼의 상위 목표는 **'변화의 속도에 확신을 주는 것'**이고, CI/CD 연결이나 테스트 선택은 방법일 뿐이에요.
- AI에게도 할 일과 함께 **왜, 어떤 제약과 우선순위로** 하는지 전달하는 게 유효해 보인대요. 다만 판단이 목표를 임의로 넓히지 않게 맡긴 범위도 함께 줘야 해요.
- 새 문제는 남들도 고민했을 가능성이 높으니 레퍼런스를 찾고, AI가 주어진 판 위에서만 답을 찾을 땐 **판 자체도 검토 대상**으로 열어 두자고 해요.

### 2. AI가 독립적으로 일하려면 어떤 기반이 필요한가?

- 같은 레포에서 폴더만 나누면 엉키기 쉬웠고, 레포·서비스·리소스를 실제로 나누면 경계가 분명해졌대요. 그런데 작업별로 레포를 복제해도 **실행 상태 DB를 공유**하는 일이 있었다며, 코드 분리가 자원 격리는 아니라고 짚어요.
- 병렬 AI 작업에선 공용 인터페이스와 담당 결과, 수정 권한을 분명히 해야 조율 대기가 줄어요.
- "하네스를 쥐어준다"는 건 도구·실행 환경·검증·피드백을 연결해 주는 거래요. 개인 노트북에선 computer use가 내 환경과 겹쳐, AI에게 **별도 컴퓨터나 클라우드 환경**을 주는 쪽으로 생각을 넓혔다고 해요.
- 스택, 인터페이스, 격리 경계 같은 **초기 선택은 이후 반복 비용**을 만들어요. 바꾸기 어려운 선택은 작은 실험으로 확인하고, 쉬운 세부 구현엔 재량을 넓히는 접근을 권해요.

### 3. 결과를 어떻게 빨리, 믿을 만하게 확인할까?

AI가 고치고 확인하는 주기가 짧을수록 일이 이어지기 쉬워요. SWC(코드 변환)나 Turborepo(작업 결과 재사용)처럼 이미 있는 수단을 찾아 쓰되, 무엇을 기다리는지 먼저 확인하고 전후를 비교하자고 해요. 공통 컴포넌트 수정과 이를 쓰는 비즈니스 로직을 다른 PR로 나누는 것처럼 **변경을 작게** 쪼개면 검증과 검토가 쉬워진대요.
